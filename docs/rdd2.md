# RDD2 developer workflow

The first common benchmark adapter implementation and its current limits are
documented in [Common flight-stack benchmark](common-benchmark.md).

This page describes the optional cross-repository Devenv workflow. RDD2 itself
remains a standalone Zephyr application: follow `src/cerebri_rdd2/README.md` to
initialize its `west.yml` and use `west update`, `west build`, and `west flash`
without Nix. The project's `flake.nix` is a separate opt-in reproducible tool
environment, while the root Devenv adds editable workspace dependencies and
task ordering.

Use one `rdd2` profile for West development, firmware, SIL builds, BIL mission
tests, and deployment:

```yaml
# devenv.local.yaml
profile: rdd2
```

On first setup, run `./setup rdd2`. It selects `rdd2` in the ignored
`devenv.local.yaml` and enters it with `devenv shell`, so later unqualified
`devenv` commands use RDD2 too. Without a local selection, use
`devenv -P rdd2 shell` and prefix one-off commands with `devenv -P rdd2`. The
profile includes both Zephyr toolchains, RDD2's isolated West workspace,
editable Synapse/CSyn/ZROS dependencies, the local Rumoca compiler, and the
FastDyn/QEMU BIL toolchain. See the root README for Devenv's current
profile-task completion limitation.

## Choose the workflow

| Goal | Entry point | Result |
| --- | --- | --- |
| Build flight firmware | `devenv -P rdd2 tasks run rdd2:firmware:build` | Cortex-M7 `mr_vmu_tropic` image |
| Configure flight firmware | `devenv -P rdd2 tasks run rdd2:firmware:configure` | Project-owned menuconfig for the hardware build |
| Run pure Modelica | `devenv -P rdd2 tasks run rdd2:simulation:modelica:test` | Modelica controller and Modelica physics executed by Rumoca |
| Run host SIL | `devenv -P rdd2 tasks run rdd2:simulation:sil:test` | 64-bit Zephyr `native_sim`, FMI 3 plant, and mission report |
| Check 32-bit host compatibility | `devenv -P rdd2 tasks run rdd2:simulation:sil:build-32` | 32-bit `native_sim` executable |
| Run closed-loop BIL | `devenv -P rdd2 tasks run rdd2:simulation:bil:test` | FastDyn/QEMU mission report for the Cortex-M7 binary |
| Compare existing matched trajectories | `RDD2_TRAJECTORY_REFERENCE=/absolute/reference.csv devenv -P rdd2 tasks run rdd2:simulation:compare` | Error gates, HTML report, and overlaid plots; no BIL dependency |
| Flash a controller | `devenv -P rdd2 tasks run rdd2:firmware:flash` | Previously built hardware image |

## West and firmware development

Build the default hardware target:

```sh
devenv -P rdd2 tasks run rdd2:firmware:build
```

The first build clones missing editable source dependencies and initializes
`.devenv/state/west/rdd2/` from RDD2's own `west.yml`. The task passes editable
Cerebri modules, CSyn, ZROS, generated Synapse C, and the local Rumoca compiler
into the project flake. Normal rebuilds reuse the source checkouts, isolated
West checkout, and project build directory.

Expected firmware artifacts are:

```text
src/cerebri_rdd2/build-mr_vmu_tropic/zephyr/zephyr.elf
src/cerebri_rdd2/build-mr_vmu_tropic/zephyr/zephyr.bin
```

Open Kconfig and rebuild without changing profiles:

```sh
devenv -P rdd2 tasks run rdd2:firmware:configure
devenv -P rdd2 tasks run rdd2:firmware:build
```

Update West revisions only when intended:

```sh
devenv -P rdd2 tasks run rdd2:workspace:update
```

RDD2 and CUBS2 never share `.west`, Zephyr, module, or model directories.

## Software-in-the-loop simulation

Build the actual RDD2 application for Zephyr's 64-bit host simulator:

```sh
devenv -P rdd2 tasks run rdd2:simulation:sil:build
```

The output is:

```text
src/cerebri_rdd2/build-native_sim/zephyr/zephyr.exe
```

Run that firmware against the event-aware FMI 3 plant generated from the same
Modelica package used by the other phases:

```sh
devenv -P rdd2 tasks run rdd2:simulation:sil:test
```

The task invokes RDD2's project-owned `sil-ci` app. The native board's current
configuration supplies the shared-memory lockstep interface and the controller
generated by Rumoca; the removed `tests/zephyr/native_sil.conf` is not needed.
The app exports `Vehicles.Rdd2.Plant`, compiles its FMI library for the host
architecture, builds the `xtask` mission runner, and writes
`src/cerebri_rdd2/artifacts/sil/mission.json` and `mission-trajectory.csv`.
Workspace-selected compiler and model sources are recorded as
`provider_mode: caller-selected`, rather than a repository-pinned qualification.
Build the 32-bit
compatibility target separately:

```sh
devenv -P rdd2 tasks run rdd2:simulation:sil:build-32
```

Its output is under `src/cerebri_rdd2/build-native_sim32/`.

Launching `zephyr.exe` alone is still intentionally incomplete: the project
runner creates and sequences `RDD2_LOCKSTEP_SHM` and advances the FMI plant.

## Binary-in-the-loop mission

Run RDD2's complete closed-loop regression with the hardware-target binary:

```sh
devenv -P rdd2 tasks run rdd2:simulation:bil:test
```

The task graph:

1. Builds FastDyn's generic Python environment, patched QEMU, plugin,
   device models, and Rumoca support.
2. Builds RDD2 for `mr_vmu_tropic` with RDD2's project-owned Kconfig and
   devicetree overlay.
3. Exports the RDD2 FMI 3 plant and builds the compiled shared-memory/FMI host.
4. Rehosts the Cortex-M7 ELF under QEMU, flies the bounded mission, checks the
   result, and writes JSON and logs.

Principal artifacts are:

```text
src/cerebri_rdd2/build-mr_vmu_tropic-fastdyn/zephyr/zephyr.elf
src/cerebri_rdd2/artifacts/bil/work/cerebri_rdd2_mission.json
src/cerebri_rdd2/artifacts/bil/mission.log
```

The BIL architecture is the ARM Zephyr control binary rehosted by FastDyn/QEMU
with Rumoca physics. It uses the same generated FMI 3 plant and mission logic
as SIL; only the firmware transport changes from a host process to rehosted ARM
memory. The Rust `physics` module is an FMI host and contains no vehicle
equations.

Build all BIL components without running the mission:

```sh
devenv -P rdd2 tasks run rdd2:simulation:bil:build
```

Adjust the project-owned mission settings with environment variables:

```sh
RDD2_FASTDYN_MISSION_DURATION_S=30 \
RDD2_FASTDYN_PLANT_DT_S=0.01 \
devenv -P rdd2 tasks run rdd2:simulation:bil:test
```

Other useful settings are `RDD2_FASTDYN_MIN_SPEEDUP`,
`FASTDYN_RDD2_TIMEOUT_SEC`, and `FASTDYN_RDD2_NETWORK_SETUP`. Network setup is
false by default because lockstep uses shared memory; enabling it adds the
privileged TAP/Zenoh communications side channel.

Fresh source syncs start FastDyn's coordinated branch at verified revision
`c235932a60a7bb839e59cac111920fb3b5cbf1aa` until the generic external-
configuration support reaches `main`. Existing source checkouts are fetched
but never switched. If an existing checkout is on `main`, create a work branch
at that revision:

```sh
devenv tasks run sources:sync:FastDyn
git -C src/FastDyn switch -c workspace/cerebri-bil \
  c235932a60a7bb839e59cac111920fb3b5cbf1aa
```

## Cross-fidelity mission comparison

Run Modelica and SIL separately with the commands above. The pinned sources
currently define different qualification missions: Modelica flies a 4 m box
at 2 m altitude for 45 seconds, while SIL flies a 0.5 m box at 1.5 m altitude
for 44 seconds. Their existing default logs are not a tracking-parity benchmark.
The Modelica qualifier writes `waypoint-local.csv` and `waypoint-global.csv`,
not the removed `mission-trajectory.csv` reference.

Once a canonical reference from the same mission is available, compare existing
logs without rebuilding or requiring the optional BIL environment:

```sh
RDD2_TRAJECTORY_REFERENCE=/absolute/path/to/matched-reference.csv \
devenv -P rdd2 tasks run rdd2:simulation:compare
```

The task requires an explicit reference to avoid silently comparing those
different missions. Both logs must use this canonical schema:

```text
time_s,x_m,y_m,z_m,roll_rad,pitch_rad,yaw_rad
```

The candidate defaults to `src/cerebri_rdd2/artifacts/sil/mission-trajectory.csv`.
The comparison bundle under
`src/cerebri_rdd2/artifacts/trajectory-comparison/` contains four PNG plots,
an HTML review report, Markdown, and machine-readable JSON. The test measures
duration, 3-D position, altitude, and wrapped attitude error and fails when a
vehicle-owned limit is exceeded.

Use `RDD2_TRAJECTORY_SIL`, `RDD2_TRAJECTORY_OUTPUT`, and the existing limit
variables to select another candidate, output directory, or acceptance budget.
`RDD2_TRAJECTORY_REFERENCE_LABEL` labels the supplied reference. A same-mission
SIL rerun is useful for testing repeatability, but does not establish Modelica
or cross-stack parity. Matching the shared mission, initial conditions, sensor
inputs, and timing remains necessary before making those comparisons.

## Flash and deploy

Flash the previously built image:

```sh
devenv -P rdd2 tasks run \
  rdd2:firmware:flash
```

Select another project-supported runner with `RDD2_FLASH_RUNNER`, for example:

```sh
RDD2_FLASH_RUNNER=jlink devenv -P rdd2 tasks run \
  rdd2:firmware:flash
```

Flashing is never a dependency of build, configure, simulation, shell entry,
or process startup.

## Exact task names

Use an exact leaf task from `devenv -P rdd2 tasks list`. A namespace
such as `rdd2:simulation` selects all descendants, including both expensive
BIL work and SIL builds. It is not a launch preset or alias.

The shared rationale and topology comparison are in
[Vehicle firmware and simulation](vehicle-development.md).
